# 项目方向与需求分析

> 基于现状分析（见《项目现状分析》）+ 联网检索的同类项目与官方资料（见《资料检索清单》）给出。

---

## 1. 现有基础决定了什么

现有代码只有一个学生表 + 注册/登录/查单，但这套**JWT 认证、统一响应、全局异常、参数校验**的骨架，恰好是所有管理系统方向都必须用的地基。因此三个方向的差异主要体现在**业务域的广度和特色功能的深度**上，地基投入（修 bug、补认证权限）三个方向完全共通。

---

## 2. 三个候选方向

### 方向 A：完整的学生信息管理系统（纵向打磨型）

| 维度 | 说明 |
|---|---|
| 目标用户 | 班主任/教务老师，管理一个或多个班级的学生档案 |
| 解决的问题 | 现在用 Excel 记学生信息，改一次传一次、查重靠肉眼、错改无法追溯 |
| 核心功能 | 学生档案 CRUD、分页搜索、班级归属、头像上传、操作日志、导入导出 Excel |
| 相比 CRUD 的特色 | 真正做"完整"：唯一索引防重、乐观锁防并发改、Excel 批量导入、变更历史审计 |
| 技术与难度 | EasyExcel、分页插件、文件存储。难度 ★★☆☆☆（最低） |
| 复用现有代码 | **~90%**：现有三张接口直接成为子系统 |
| 成本/学习难点 | 成本最低；难点仅在 Excel 导入的脏数据校验 |
| 适合用途 | 课程项目 ✅；作品集 △（太常见，同类开源项目上千个）；长期项目 ✗ |

### 方向 B：学生-班级-课程-成绩-考勤一体化平台（业务广度型）

| 维度 | 说明 |
|---|---|
| 目标用户 | 中小培训机构/学校教务：管学生、排课、记成绩、点考勤 |
| 解决的问题 | 学生、课程、成绩、考勤分散在多个表格里，相互对不上（学生退课了成绩还在算） |
| 核心功能 | 在 A 基础上增加：班级管理、课程管理、选课关系、成绩录入（一人一课多成绩）、考勤打卡、课表视图 |
| 相比 CRUD 的特色 | **多表关系建模**（5-6 张表、外键与联动校验）、事务一致性（退课+成绩处理）、角色权限（admin/teacher/student 三角色看不同数据） |
| 技术与难度 | 多表关联查询、MyBatis-Plus 分页+条件构造器进阶、RBAC。难度 ★★★☆☆ |
| 复用现有代码 | **~70%**：学生模块原样保留，新增 4-5 个业务模块 |
| 成本/学习难点 | 工作量最大但每一步都是标准套路；难点是表关系设计和角色权限，这正是最值得学的 |
| 适合用途 | 课程项目 ✅；**作品集 ✅（能展示数据库设计和权限设计能力）**；长期项目 ✅ |

### 方向 C：学习数据统计与成绩分析平台（特色深度型）

| 维度 | 说明 |
|---|---|
| 目标用户 | 学生和家长（看趋势）、老师（看班级分布） |
| 解决的问题 | 录入成绩≠利用成绩：看不出退步趋势、薄弱科目、班级排名变化 |
| 核心功能 | 在 B 的成绩模块之上：成绩趋势折线图、班级分布直方图、排名变化、薄弱知识点标记、学生画像页 |
| 相比 CRUD 的特色 | **数据统计与可视化**（SQL 聚合分析 + ECharts 图表），答辩演示效果最好 |
| 技术与难度 | SQL 聚合/GROUP BY、ECharts 5、前后端联调。难度 ★★★★☆（依赖 B 的数据模型） |
| 复用现有代码 | **~50%**：需要先有 B 的成绩数据才有东西可分析 |
| 成本/学习难点 | 成本最高；难点是统计 SQL 的正确性（排名并列、缺考处理）和图表联调 |
| 适合用途 | 课程项目 ✅（演示惊艳）；作品集 ✅；长期项目 ✅（可加 AI 分析等卖点） |

| 评价维度 | A 纵向打磨 | B 一体化平台 | C 数据分析 |
|---|---|---|---|
| 可行性（现有基础+你的水平） | ★★★★★ | ★★★★☆ | ★★★☆☆ |
| 学习价值（学到真实开发流程） | ★★★☆☆ | ★★★★★（多表建模/事务/权限全是重点） | ★★★★☆（统计SQL/可视化） |
| 功能实用性（真有人用） | ★★★☆☆ | ★★★★☆ | ★★★★☆（依赖数据量） |
| 完成难度（越低越好） | ★★★★★（最易） | ★★★☆☆（适中，工作量最大但无技术死角） | ★★☆☆☆（最险） |
| 后续扩展能力 | ★★☆☆☆ | ★★★★★（C 是它的天然延伸） | ★★★★☆ |
| 演示/答辩效果 | ★★☆☆☆ | ★★★★☆ | ★★★★★ |

## 4. 明确推荐：方向 B（一体化平台），以 C 为二期延伸

**推荐 B，并把 C 定为 B 完成后的二期目标，理由有四条：**

1. **复用最大化，学习价值最大化**：你现有的学生+JWT 模块 100% 是 B 的地基。B 新增的每一块（多表关系、事务、角色权限、分页查询）恰好都是 Spring Boot 后端面试和实际工作的核心考点——学的东西没有一项是白费的。
2. **风险可控**：B 的每个模块都是成熟套路（参考检索到的多个同类开源项目，见资料清单），不存在"卡死"的技术点；而 C 直接做没有数据支撑，统计页会是空壳，项目容易烂尾。
3. **天然的成长路线**：B 做完 → 数据模型健在 → 加上 ECharts 和统计 SQL 就升级成 C。等于一条路线吃到两个方向的成果，作品集里可以写成"一体化平台 + 数据分析"两层亮点。
4. **成本符合约束**：全程零付费服务（MySQL/前端/ECharts 全免费开源），在你现有 Windows + IDEA + Maven 环境即可完成，无需引入 Redis/MQ/微服务。

**不推荐 A 作为终点**：它太常见，作品集辨识度低；但它包含的工作（修复现有问题、完善学生模块）100% 是 B 的第一步，所以作为"第一阶段"被完整吸收进 B。
**不推荐 C 作为起点**：依赖 B 的数据模型，跳过 B 直接做 C 等于空中楼阁。

### 推荐路线一览

```
阶段0 修复地基(现状问题) → 阶段1 学生模块完善(≈方向A)
→ 阶段2-4 班级/课程/成绩/考勤 + 角色权限(=方向B)
→ 二期(可选) ECharts 统计分析(=方向C)
```

详细的功能清单、数据库表设计、API 设计见《技术方案与数据库设计》；分阶段的任务拆解见《开发路线图》。
