# ClassHub 部署说明

> 本文档所有命令均在本机实测过。阶段 6.4 验证了 fat-jar 打包与直连启动；
> 阶段 10 补上了**真正的生产形态**：nginx 静态托管 + API 反代（16 项验证全过，见第三节）。

## 一、产物

| 产物 | 路径 | 说明 |
| --- | --- | --- |
| 后端 fat-jar | `target/demo-0.0.1-SNAPSHOT.jar`（约 37 MB） | `mvnw package` 生成，内嵌 Tomcat，**无需单独装服务器** |
| 前端静态文件 | `web/dist/` | `pnpm build` 生成，任意静态服务器可托管 |
| Nginx 配置 | `deploy/nginx/nginx.conf` | 单端口同时服务前端与 API，已实测 |
| SQL 迁移 | `sql/V1__init.sql` ~ `sql/V13__*.sql` | 按序号执行即可从零建库 |
| Schema 校验 | `sql/verify_schema.sql` | **只读**，一条命令查出环境与代码是否一致 |

> **V10 是可选的演示数据**：`V10__seed_demo_data.sql` 会造 2 个班 / 20 名学生 / 3 门课 / 80 条选课 / 160 条成绩，用于演示图表效果。**生产环境不要执行**，它会把演示学生混进真实数据。只跑 V1–V9 + V11–V13 就能得到完整可用的空系统。

### ⚠️ 迁移脚本会漏跑——先跑 verify_schema.sql

2026-11-02 发生过一次真实事故：代码已用到 `attendance` / `leave_request` 表和 `score.deleted` 列，但库**落后了 5 个脚本**，导致「成绩分析」「考勤」「请假」三个页面全部 500（`ERROR 1054 Unknown column 's.deleted'`）。

项目用编号脚本手工迁移，**没有任何机制记录哪些跑过**。换机器、换库、或只是忘了执行，就会漂移。所以每次拉新代码后，先跑这一条：

```bash
mysql -h 127.0.0.1 -P 3306 -u root -p --default-character-set=utf8mb4 --table -e "source sql/verify_schema.sql"
```

只看最后一节的 `total_mismatches`：

- `0` → 环境与代码一致，可以启动
- `> 0` → 上面各节的 `ok=0` 行会直接告诉你缺什么、该执行哪个脚本

**为什么不能只靠 `CREATE TABLE IF NOT EXISTS`**：这是最隐蔽的漂移来源。`V2__schema_refactor.sql` 里 `score` 的建表语句确实写了 `deleted` 列，但表已存在时整条语句被跳过——**建表语句里的字段后来改过，对已存在的表完全无效**。这就是为什么 `score.deleted` 需要单独的 `V13__score_deleted_restore.sql` 用 `ALTER TABLE` 补。

### 执行顺序（有依赖，不能乱）

| 顺序 | 脚本 | 说明 |
| --- | --- | --- |
| 1 | `V13__score_deleted_restore.sql` | **必须先跑**：V7 的前置查重查询引用了 `deleted` 列 |
| 2 | `V7__score_unique_exam_type.sql` | 成绩唯一键改为「一人一考试类型」，否则录完期中录期末会 409 |
| 3 | `V8__pwd_change_time_millis.sql` | 改密时间提到毫秒，否则同一秒内改密旧 token 仍有效（安全漏洞） |
| 4 | `V9__attendance.sql` | 建考勤表 |
| 5 | `V11__normalize_exam_type.sql` | 把历史中文 `exam_type` 归一化为 `final/midterm/makeup` |
| 6 | `V12__leave_request.sql` | 建请假表 |

**V6 可以选择跳过**：`V6__enrollment_physical_delete.sql` 会 `DROP COLUMN enrollment.deleted`。该列当前无任何代码引用（`Enrollment` 实体没有该字段），删掉它没有功能收益，而 `DROP COLUMN` 是不可逆的。保留一个无害的残留列比执行破坏性变更更稳妥——但如果要严格对齐 schema，可以执行它。

## 二、后端启动（fat-jar）

```bash
# 1. 打包（测试已在 6.1 全绿，发布时可 -DskipTests 提速）
mvnw.cmd package -DskipTests

# 2. 启动（生产配置全部用命令行参数/环境变量注入，不改 jar 内文件）
set JWT_SECRET=<强随机Base64串，至少32字节>
"C:\Program Files\Java\jdk-26.0.1\bin\java.exe" -jar target\demo-0.0.1-SNAPSHOT.jar ^
  --spring.datasource.password=<生产库密码> ^
  --server.port=8080
```

### ⚠️ 已踩过的坑（部署必读）

1. **UnsupportedClassVersionError（class file version 69.0 vs 61.0）**
   项目按 JDK 26 编译（class 版本 69），PATH 上的 `java` 是 17（只认到 61）。
   **解法**：运行 fat-jar 必须用与编译版本一致或更高的 JDK——用完整路径调
   `jdk-26.0.1\bin\java.exe`，或把 `JAVA_HOME`/`PATH` 指到 JDK 26。
   **通用规律**：`java -jar` 用的 JRE 版本 ≥ 编译目标版本。

2. **JWT_SECRET 不能用代码里的本地默认值**
   `application.yaml` 里的默认 secret 仅限开发；生产必须注入强随机值（≥32 字节 Base64），
   否则 token 可被伪造。

3. **数据库密码通过 `--spring.datasource.password` 或环境变量 `DB_PASSWORD` 注入**
   不要把生产密码写进任何入库文件。

## 三、前端部署（两种方式）

### 方式 A：开发演示（最简）

直接 `cd web && pnpm dev`——Vite dev server 自带 8080 代理，适合本机演示，不适用于生产。

### 方式 B：生产（Nginx 静态托管 + API 反代）✅ 已实测

```bash
cd web && pnpm build     # 产物在 web/dist/
```

完整可用的配置在仓库里：**`deploy/nginx/nginx.conf`**（本机已用 nginx 1.31.8 实测通过）。
下面只讲三个最容易搞错的地方，完整注释见该文件。

#### 坑 1：两个 `location /` 会让 nginx 直接拒绝启动

上一版本文档写的是「一个 `location /` 托管静态、一个 `location /` 反代后端」——
nginx **不允许重复的 location**，会报：

```
nginx: [emerg] duplicate location "/"
```

正确做法是按前缀分流，前端与 API 各占一个 location：

```nginx
server {
    listen 8088;
    root  D:/software/demo/web/dist;

    # 后端 API：/api/ 开头 → 转发后端，并去掉 /api 前缀
    location /api/ {
        proxy_pass http://127.0.0.1:8080/;
        proxy_set_header Host            $host;
        proxy_set_header X-Real-IP       $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    # 前端：Vue history 路由回退
    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

#### 坑 2：`proxy_pass` 末尾的斜杠决定了要不要剥前缀

| 写法 | `/api/student` 实际转发到 | 结果 |
| --- | --- | --- |
| `proxy_pass http://127.0.0.1:8080/;`（**有**斜杠） | `/student` | ✅ 正确，与开发期 vite 的 `rewrite` 一致 |
| `proxy_pass http://127.0.0.1:8080;`（**无**斜杠） | `/api/student` | ❌ 后端没有 `/api` 前缀 → 404 |

因为规则与开发期一致，**前端代码一行都不用改**（`request.js` 里 `baseURL: '/api'` 原样上生产）。
上一版本文档说「需把 axios baseURL 改为同域相对路径」——**这句是错的，已实测无需改动**。

#### 坑 3：`expires` 与 `add_header Cache-Control` 不能叠加

```nginx
expires 1y;
add_header Cache-Control "public, immutable";
```

会输出**两个** `Cache-Control` 响应头：

```
Cache-Control: max-age=31536000
Cache-Control: public, immutable
```

浏览器通常只取第一个，`immutable` 等于白写。只保留 `add_header`：

```nginx
location /assets/ {
    add_header Cache-Control "public, max-age=31536000, immutable";
    try_files $uri =404;
}
```

> 缓存策略的分工：带 content hash 的 `/assets/*` 缓存一年；
> `index.html` 必须 `no-store`——它是所有哈希资源的入口，一旦被缓存，
> 发版后用户仍加载旧 index.html，引用已删除的旧 js，直接白屏。

### Windows 本机启动 nginx 的完整命令

```powershell
# 1. 下载解压（本机放在 D:\software\_tools\nginx-1.31.8）
#    http://nginx.org/download/nginx-1.31.8.zip

# 2. 把 nginx 自带的 conf\mime.types 复制到 deploy\nginx\ 下
#    （配置里 include mime.types 是相对路径，找不到会报 CreateFile failed）

# 3. 检查语法（-t 只是检查，不启动）
cd D:\software\_tools\nginx-1.31.8
.\nginx.exe -t -c "D:\software\demo\deploy\nginx\nginx.conf"

# 4. 启动 / 改配置后平滑重载 / 停止
.\nginx.exe    -c "D:\software\demo\deploy\nginx\nginx.conf"
.\nginx.exe -s reload -c "D:\software\demo\deploy\nginx\nginx.conf"
.\nginx.exe -s stop   -c "D:\software\demo\deploy\nginx\nginx.conf"
```

> Windows 上 nginx 是**后台进程**（启动后命令行立刻返回），日志在
> `deploy/nginx/logs/classhub-access.log` 和 `classhub-error.log`。
> 排查 502 时先看 error log——它会直接写 `connect() failed (10061)` 之类的具体原因。
