## 五、本轮发现并修复的新缺陷

### 5.1 改密后旧 token 未失效（严重度：高）

**现象**：执行"登录 → 立刻改密 → 用旧 token 访问"这条链路，旧 token 仍然返回 200。

**定位过程**：

1. 先怀疑 Redis 缓存：`TokenBlacklistService.getPwdChangeTime` 有 60 秒缓存，改密时调了 `invalidatePwdTimeCache` 主动删缓存——代码逻辑正确，排除。
2. 打日志看时间戳：登录拿到的 token `iat = 1793542359`，改密后新 token 的 `iat` **也是 1793542359**，两者完全相同。
3. 根因：**JWT 的 `iat` 标准声明只精确到秒**（RFC 7519 规定 NumericDate 是秒级），MySQL `datetime` 默认也到秒。同一秒内登录再改密，`iat == pwd_change_time`，判断 `iat.isBefore(pwdChangeTime)` 为 false → 旧票被当成新票放行。
4. 次要原因：原代码有个 `iat.plusSeconds(1).isBefore(...)` 的"1 秒宽容窗口"，本意是防止刚签发的新票被误杀，但副作用正是让**改密前 1 秒内签发的旧票继续可用**——那恰恰是最该被踢下线的一批。

**修复**（3 处改动 + 1 个迁移）：

| 文件 | 改动 |
| --- | --- |
| `src/main/java/com/example/demo/util/JwtUtil.java:40` | 签发时额外写一个毫秒 claim `iatMs` |
| `src/main/java/com/example/demo/util/JwtUtil.java:64-70` 新增 `getIssuedAtMillis(Claims)` | 优先读 `iatMs`；老 token 无此 claim 时退回标准 `iat`（这类票本来就活不过 2 小时） |
| `src/main/java/com/example/demo/config/JwtAuthenticationFilter.java:70` | 改用 `jwtUtil.getIssuedAtMillis(claims)` 而非 `claims.getIssuedAt().toInstant()` |
| `src/main/java/com/example/demo/service/TokenBlacklistService.java:84` | 去掉 `plusSeconds(1)` 宽容窗口，改严格 `isBefore` |
| `sql/V8__pwd_change_time_millis.sql`（新增） | `pwd_change_time` 改为 `DATETIME(3)` |

**验证**：修复后 43/46 两条用例通过，且新 token 立即可用（没有因为精度提升而误杀刚签发的票）。

### 5.2 三处 `add` 方法缺事务（严重度：中）

`ClazzServiceImpl.add`、`CourseServiceImpl.add`、`ScoreServiceImpl.add` 都是"先查重再插入"的两步操作，但没有 `@Transactional`。虽然单条 insert 本身是原子的，但"查重→插入"这个组合在并发下需要靠数据库唯一键兜底（代码里已有 `catch DuplicateKeyException`），补事务让异常路径的语义更清晰。

已在三个方法上补 `@Transactional`（`ScoreServiceImpl` 还需要它保证"查选课记录存在 → 查重 → 插入"三步的读一致性）。

### 5.3 「我的成绩」在课程查不到时 500（严重度：中，补写单元测试时发现）

**现象**：`ScoreServiceImpl.query()` 组装 `enrollmentId → 课程名` 映射时用了 `Collectors.toMap`：

```java
Map<Long, String> courseNameByEnrollment = enrollments.stream()
        .collect(Collectors.toMap(Enrollment::getId,
                e -> courseNameById.get(e.getCourseId())));
```

`Collectors.toMap` 内部走 `Map.merge`，**value 为 null 时直接抛 `NullPointerException`**。而 `courseNameById.get()` 在"选课指向的课程查不到"时必然返回 null。

**触发场景**（都是真实可能发生的）：
1. 课程被逻辑删除（`selectBatchIds` 按 `@TableLogic` 自动过滤掉），但历史选课记录还在；
2. 早期测试/手工操作留下的脏数据，`enrollment.course_id` 指向不存在的课程。

此时学生一打开"我的成绩"，服务端就 500——整个页面白屏，连已有的分数都看不到。

**为什么之前没发现**：端到端测试用的数据是"选课和课程都正常"的干净数据，走不到这条分支。是补写单元测试时用 `assertDoesNotThrow` 才撞出来的——这正是单元测试的价值：它让你能低成本地构造"不正常的输入"，而真实环境里造这种脏数据很麻烦。

**修复**：换成显式的可空 `HashMap` 填充，课程名取不到就让该行显示空，不影响其余数据。

```java
Map<Long, String> courseNameByEnrollment = new HashMap<>();
for (Enrollment e : enrollments) {
    courseNameByEnrollment.put(e.getId(), courseNameById.get(e.getCourseId()));
}
```

**验证**：`ScoreServiceImplTest.query_missingCourseDoesNotThrow` 覆盖此分支，修复前抛 NPE、修复后通过。

**这条的教训**：`Collectors.toMap` 是个"看起来很方便、但对 null 零容忍"的 API。凡是 value 可能为 null 的映射，用 `HashMap` 手动 put，或者用 `Collectors.toMap(k, v, (a,b)->a, HashMap::new)` 并确保 value 非空。这个坑在 Java 项目里非常常见。
