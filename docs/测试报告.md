### 3.8 Controller 切片测试（150 条，10 个类）

单元测试把 Service 挖空来测，Controller 层反而一直没测——HTTP 状态码、`@PreAuthorize` 权限、参数绑定这些只靠端到端兜着，而端到端要真库 + 真 Redis，跑一次半分钟，改代码时不会想跑。

所以补了这一层：`@WebMvcTest` 起一个"只有 Web 层"的 Spring 切片，Service 用 `@MockitoBean` 打桩，**但安全过滤链是真的**——真实签发 JWT、真实走 `JwtAuthenticationFilter`、真实经过 `SecurityConfig` 的规则和 `@PreAuthorize` 拦截。这样权限矩阵才是被真的验证过，而不是"我 mock 了一个已登录用户"。

**这一层最值得说的一条：`GET /scores/my` 是"只有学生"能访问的**（`hasRole('STUDENT')`）。教师访问会 403，看起来反直觉——但这个接口不接受任何 id 参数，完全依赖 token 里的身份，教师没有"自己的成绩"，放开只会返回空列表把问题藏起来。测试把这条边界钉住了。`/stats/my/trend`、`/attendance/my` 同理。

**`AttendanceControllerTest` 额外锁住了两件只在 HTTP 层才暴露的事**：

1. **嵌套校验是否真的生效**：`items` 是 `List<Item>`，如果漏了 `@Valid`，列表内每个元素的 `@NotNull`/`@Max` 会**静默失效**——`status: 9` 能一路穿过 Controller 进 Service。只有发真实 HTTP 请求才能验证这条。顺带把写法从 `@Valid List<Item>` 改成了 `List<@Valid Item>`（Hibernate Validator 6.1+ 推荐，且老写法会打弃用警告）。
2. **缺必填参数必须是 400 而不是 500**：这条测试**抓到了一个真实缺陷**——见 5.5。

**为什么每个测试类都要自己写一段 `SliceConfig`**：`@WebMvcTest` 默认会拿 `@SpringBootApplication` 启动类当配置来源，而启动类上有 `@MapperScan`，会把 6 个 Mapper 全注册进切片，切片里没有 `SqlSessionFactory`，直接启动失败。用 `@ContextConfiguration(classes = SliceConfig.class)` 换掉配置来源，`@MapperScan` 就不执行了——比给 6 个 Mapper 逐个打桩干净得多。代价是组件扫描也不再执行，所以 Controller 和 `GlobalExceptionHandler` 要在 `@Import` 里显式列出来。

**踩到的两个坑（都是"看起来像业务 bug，其实是测试配置"）**：

1. 一开始只 `@Import` 了 `SecurityConfig`，报 `No qualifying bean of type 'HttpSecurity'`。切片不会自动启用 Security Web 基础设施，需要 `@EnableWebSecurity`。**不能用 `@MockitoBean HttpSecurity` 糊过去**——那样 `.csrf()`、`.authorizeHttpRequests()` 全作用在 mock 上，`http.build()` 返回空壳，安全规则一条都不生效，测试会全绿但什么都没验证。
2. `ClazzResponse.teacherId` 的类型是 `Integer`（历史遗留，和 `CourseResponse` 的 `Long` 不一致），测试里传 `long` 常量编译不过。改测试时顺手记下这个不一致，没有去改生产代码。

**纯 Mockito 单测的一个隐藏门槛**：`AttendanceServiceImplTest` 一开始 3 个用例报 `can not find lambda cache for this entity`。原因是 `LambdaQueryWrapper` 需要 MyBatis-Plus 的实体元数据（表名/列名映射）才能把 `Attendance::getStudentId` 翻译成列名，而纯 Mockito 环境没有 Spring 上下文，这份元数据没初始化。解法是在 `@BeforeAll` 里手动调一次 `TableInfoHelper.initTableInfo(assistant, Attendance.class)`。**注意必须用 `@BeforeAll` + static**，每个方法都初始化会重复注册。

> 说明：Controller 测试不连数据库、不连 Redis，312 条后端测试合计约 12 秒。

### 3.9 LeaveServiceImplTest（22 条）：状态机与考勤联动

请假模块的复杂度几乎全在**状态机**和**考勤联动**这两处，所以断言重点也在那儿。

| 用例组 | 条数 | 验证点 |
| --- | --- | --- |
| create 校验 | 6 | 起止颠倒 400；超 30 天 400；**正好 30 天放行（边界不能多拦一天）**；课程不存在 404；未选课 400；区间重叠 409 |
| create 成功 | 1 | 初始状态 0；**studentId 来自 token 而不是 DTO**（防 IDOR 越权） |
| approve 终态 | 3 | 已通过/已驳回/已撤销的再审批一律 400，且**不产生任何写操作** |
| ★ approve 写考勤 | 4 | 无记录时逐天补建 status=3；有记录时改成请假不重复插入；已是请假则跳过；同一天多节次全部改 |
| ★ reject 不写考勤 | 1 | 状态改 2，且 `attendanceMapper` 的 insert/updateById/selectList **一次都没被调用** |
| cancel | 4 | 不存在 404；**撤别人的 403**；已通过不能撤 400；成功改 3 |

**为什么 `reject` 那条测试要断言"一次都没被调用"而不是"结果对不对"**：驳回时不碰考勤是**否定性约束**——它错了不会立刻报错，而是悄悄让学生的旷课记录被"洗白"成请假。这种错误在界面上完全看不出来（请假列表显示"已驳回"，考勤显示"请假"，两个页面各自自洽）。只有用 `verify(..., never())` 把它钉死，未来谁在 reject 里顺手加一句考勤同步就会立刻红。

**为什么 `approve` 要测"同一天多节次"**：请假是按天的，考勤是按节次的。如果只改 `session_no=1`，学生请了假但第二节课还是"未点名"，老师打开名单看到矛盾状态。这条测试锁住"该日期所有节次都改成请假"。

**Mockito 的两个坑**（写这组测试时踩到，值得记住）：

1. **`selectById` 要用 `any()` 而不是 `anyLong()`**：创建流程里 id 来自 `insert` 回填，若打桩没回填就是 `null`，`anyLong()` 匹配不上 null，会报 `PotentialStubbingProblem`（看起来像业务 bug，其实是打桩参数类型不匹配）。
2. **`insert` 必须打桩回填 id**：真实 MyBatis-Plus 会把自增主键回写到实体，纯 Mockito 不会。不回填的话，后续 `selectById(entity.getId())` 查的是 `null`，返回 null，VO 就空了。用 `thenAnswer` 手动 `setId`。

这两个类是为 Redis 降级改造（见 5.4）配套写的。降级逻辑最容易被后续重构"顺手清理"掉，而它失效时的表现（全站 401 死循环）在单元测试之外很难察觉，所以值得单独钉住。

| 用例组 | 条数 | 验证点 |
| --- | --- | --- |
| revoke | 4 | 正常时双写本地+Redis；token 无效/已过期时静默忽略；**Redis 抛异常时登出在本实例内仍生效** |

**Mockito 的两个坑**（写这组测试时踩到，值得记住）：

1. `opsForValue().set(...)` 返回 `void`，**不能用 `when(...)` 打桩**，必须用 `doThrow(...).when(mock).set(...)`。用 `when` 会直接编译失败（"此处不允许使用 void 类型"）。
2. 已经用 `when(...).thenThrow(...)` 打桩过的方法，**想改成正常返回必须用 `doReturn(...).when(...)`**。因为 `when(mock.hasKey(...))` 这一行本身就会调用一次方法，把之前埋的异常抛出来——测试会报 `RedisConnectionFailureException` 而不是断言失败，非常容易误判成产品 bug。

**第 92、93 条是这个功能存在的全部意义**：请假批了但考勤还记旷课，等于白批。第 93 条进一步验证了**区间内每一天**都被写入，不是只写第一天——否则学生请三天假，只有第一天被保护，后两天照样被记旷课。

**第 98 条是第 92 条的反面**：驳回必须**不**碰考勤。如果驳回也写了「请假」，等于学生自己给自己批假，审批流程彻底失效。这条测试和单元测试里的 `verify(..., never())` 是同一件事的两层保障。

**第 95 条值得单独说**：它禁止"已通过 → 驳回"。这个限制看起来过于严格（现实中确实有撤销已批假期的需求），但不这么做会产生**数据不一致**：请假记录说"已驳回"，考勤表里却留着"请假"状态，两个页面各自自洽、加起来矛盾，而且没人能发现。真要支持撤销已批假期，正确做法是新增一个"撤销审批"的流转，同时把考勤状态回滚——那是另一个功能，不是让终态可逆。

**第 102 条返回 403 而不是 404**：如果返回 404，合法用户会困惑（"我的申请怎么不见了"）。403 说明"记录在，但不是你的"，语义更准确。代价是泄露了"这个 id 存在"这一信息——在请假这种低敏感度场景可以接受；如果是身份证号之类的敏感资源，则应统一返回 404 以避免枚举。

## 五、本轮发现并修复的新缺陷

### 5.1 改密后旧 token 未失效（严重度：高）

**现象**：执行"登录 → 立刻改密 → 用旧 token 访问"这条链路，旧 token 仍然返回 200。

**定位过程**：

1. 先怀疑 Redis 缓存：`TokenBlacklistService.getPwdChangeTime` 有 60 秒缓存，改密时调了 `invalidatePwdTimeCache` 主动删缓存——代码逻辑正确，排除。
2. 打日志看时间戳：登录拿到的 token `iat = 1793542359`，改密后新 token 的 `iat` **也是 1793542359**，两者完全相同。
3. 根因：**JWT 的 `iat` 标准声明只精确到秒**（RFC 7519 规定 NumericDate 是秒级），MySQL `datetime` 默认也到秒。同一秒内登录再改密，`iat == pwd_change_time`，判断 `iat.isBefore(pwdChangeTime)` 为 false → 旧票被当成新票放行。
4. 次要原因：原代码有个 `iat.plusSeconds(1).isBefore(...)` 的"1 秒宽容窗口"，本意是防止刚签发的新票被误杀，但副作用正是让**改密前 1 秒内签发的旧票继续可用**——那恰恰是最该被踢下线的一批。

**修复**（3 处改动 + 1 个迁移）：

| 文件 | 改动 |
| --- | --- |
| `src/main/java/com/example/demo/util/JwtUtil.java:40` | 签发时额外写一个毫秒 claim `iatMs` |
| `src/main/java/com/example/demo/util/JwtUtil.java:64-70` 新增 `getIssuedAtMillis(Claims)` | 优先读 `iatMs`；老 token 无此 claim 时退回标准 `iat`（这类票本来就活不过 2 小时） |
| `src/main/java/com/example/demo/config/JwtAuthenticationFilter.java:70` | 改用 `jwtUtil.getIssuedAtMillis(claims)` 而非 `claims.getIssuedAt().toInstant()` |
| `src/main/java/com/example/demo/service/TokenBlacklistService.java:84` | 去掉 `plusSeconds(1)` 宽容窗口，改严格 `isBefore` |
| `sql/V8__pwd_change_time_millis.sql`（新增） | `pwd_change_time` 改为 `DATETIME(3)` |

**验证**：修复后 43/46 两条用例通过，且新 token 立即可用（没有因为精度提升而误杀刚签发的票）。

### 5.2 三处 `add` 方法缺事务（严重度：中）

`ClazzServiceImpl.add`、`CourseServiceImpl.add`、`ScoreServiceImpl.add` 都是"先查重再插入"的两步操作，但没有 `@Transactional`。虽然单条 insert 本身是原子的，但"查重→插入"这个组合在并发下需要靠数据库唯一键兜底（代码里已有 `catch DuplicateKeyException`），补事务让异常路径的语义更清晰。

已在三个方法上补 `@Transactional`（`ScoreServiceImpl` 还需要它保证"查选课记录存在 → 查重 → 插入"三步的读一致性）。

### 5.3 「我的成绩」在课程查不到时 500（严重度：中，补写单元测试时发现）

**现象**：`ScoreServiceImpl.query()` 组装 `enrollmentId → 课程名` 映射时用了 `Collectors.toMap`：

```java
Map<Long, String> courseNameByEnrollment = enrollments.stream()
        .collect(Collectors.toMap(Enrollment::getId,
                e -> courseNameById.get(e.getCourseId())));
```

`Collectors.toMap` 内部走 `Map.merge`，**value 为 null 时直接抛 `NullPointerException`**。而 `courseNameById.get()` 在"选课指向的课程查不到"时必然返回 null。

**触发场景**（都是真实可能发生的）：
1. 课程被逻辑删除（`selectBatchIds` 按 `@TableLogic` 自动过滤掉），但历史选课记录还在；
2. 早期测试/手工操作留下的脏数据，`enrollment.course_id` 指向不存在的课程。

此时学生一打开"我的成绩"，服务端就 500——整个页面白屏，连已有的分数都看不到。

**为什么之前没发现**：端到端测试用的数据是"选课和课程都正常"的干净数据，走不到这条分支。是补写单元测试时用 `assertDoesNotThrow` 才撞出来的——这正是单元测试的价值：它让你能低成本地构造"不正常的输入"，而真实环境里造这种脏数据很麻烦。

**修复**：换成显式的可空 `HashMap` 填充，课程名取不到就让该行显示空，不影响其余数据。

```java
Map<Long, String> courseNameByEnrollment = new HashMap<>();
for (Enrollment e : enrollments) {
    courseNameByEnrollment.put(e.getId(), courseNameById.get(e.getCourseId()));
}
```

**验证**：`ScoreServiceImplTest.query_missingCourseDoesNotThrow` 覆盖此分支，修复前抛 NPE、修复后通过。

**这条的教训**：`Collectors.toMap` 是个"看起来很方便、但对 null 零容忍"的 API。凡是 value 可能为 null 的映射，用 `HashMap` 手动 put，或者用 `Collectors.toMap(k, v, (a,b)->a, HashMap::new)` 并确保 value 非空。这个坑在 Java 项目里非常常见。

### 5.4 Redis 故障导致全站不可用（严重度：高，本轮主动加固）

**这不是"修了一个 bug"，而是把一个已知单点补上了。** 上一版报告 R1 风险里写着"Redis 挂了会导致所有带 token 请求失败"，这次做了故障注入实测，确认影响比描述的更严重。

**故障注入方式**：真实启动应用，**故意不启动 Redis**（6379 无监听），MySQL 正常。用 curl 打接口。

**改造前的实际表现**（第 1 步实测）：

```
GET /student?page=1&size=5  带合法 token
→ HTTP 401
→ {"code":401,"message":"未登录或登录已过期","data":null}
```

日志：`RedisConnectionFailureException: Unable to connect to Redis`，堆栈落在 `TokenBlacklistService.isRevoked(TokenBlacklistService.java:65)`。

**为什么 401 比 500 更糟**：500 至少是个"服务器出错了"的明确信号；401 会被前端 `request.js` 解释成"你的登录过期了"，于是**清 token → 跳登录页 → 用户重新登录成功 → 下一个请求又 401 → 再跳登录页**。用户会陷入死循环，而且永远不知道是缓存服务挂了。

**改造方案**（`TokenBlacklistService` 重写 + 新增 `common/LocalExpiringCache`）：

| 手段 | 作用 |
| --- | --- |
| 降级策略 = 放行 | Redis 不可用时 `isRevoked` 返回 false。取舍：拒绝一切请求 = 100% 用户不可用；放行 = 极少数已登出 token 多活几分钟（token 本身 2 小时过期）。后者影响面小得多 |
| 本地兜底缓存 | `revoke` 时无论 Redis 是否可用都写本地，保证**故障期间登出在本实例内立即生效** |
| 熔断器 | 失败后 10 秒冷却，期间**直接跳过 Redis**。只 try-catch 不够——连接超时 2 秒，每个请求都等 2 秒会让系统"可用但极慢"，比直接失败更难排查 |
| 改密划线回源 DB | 改密时间的权威来源本来就是 MySQL，Redis 只是读缓存。Redis 挂了直接查 DB，**结果完全正确**，不是"凑合" |
| 清缓存吞异常 | `invalidatePwdTimeCache` 在 `@Transactional` 事务内被调用，抛异常会让"密码已改"整体回滚。所以对 Redis 异常一律吞掉只记日志 |

**为什么自己写缓存而不引 Caffeine**：本地 Maven 仓库里没有 Caffeine（离线构建会失败），而且这里只需要「put/get/remove + TTL + 容量上限」四件事，80 行讲得清。真到需要统计命中率、异步刷新、权重淘汰时再换。

**改造后实测（6 项全过）**：

| # | 场景 | 结果 |
| --- | --- | --- |
| 1 | Redis 停机，登录 | 200，正常拿到 token（登录路径不碰 Redis） |
| 2 | Redis 停机，带 token 查学生列表 | **200 + 真实数据**（改造前 401） |
| 3 | 连续 3 次请求耗时 | 204ms → 37ms → 31ms（熔断生效，不再等连接） |
| 4 | Redis 停机，登出后用旧 token 请求 | 401（**本地黑名单生效**，不是放行） |
| 5 | Redis 停机，改密 | 200；旧 token 立刻 401；新密码可登录 |
| 6 | Redis 恢复后 | 自动退出降级，日志 `Redis 已恢复，退出降级模式` |

**已知局限（诚实说明）**：
- 本地兜底是**单实例**的。多实例部署时，A 实例登出的 token，B 实例在 Redis 故障期间看不到——会多活到 token 自然过期。这是"可用性优先"的必然代价，也是为什么 Redis 恢复后要立刻回到共享存储。
- 熔断的 10 秒窗口内，即使 Redis 已经恢复，也要等窗口结束才重新试探。代价是"恢复慢 10 秒"，换来的是"故障期间不拖慢每个请求"。

### 5.5 缺少必填请求参数返回 500 而不是 400（严重度：中，写 Controller 测试时发现）

**现象**：`GET /attendance/stats`（不带 `courseId`）返回 **500「服务器内部错误」**，期望是 400。

**定位**：`@RequestParam Long courseId` 默认必填，缺参数时 Spring 抛 `MissingServletRequestParameterException`。而 `GlobalExceptionHandler` 里没有这个异常的转换规则——它落进了最后的 `Exception` 兜底，变成 500。

**为什么严重度算中而不是低**：这是**排查成本极高的一类误判**。客户端看到 500 会去查服务端日志、怀疑数据库挂了、重启服务；而真实原因只是少传了一个参数。已有 51 条端到端测试都没发现它，因为那些用例都规规矩矩传了参数——**只有"故意不传参数"的测试才会撞上**。

**修复**（1 处）：

```java
@ExceptionHandler(MissingServletRequestParameterException.class)
public ResponseEntity<Result<Void>> handleMissingParam(MissingServletRequestParameterException e) {
    return ResponseEntity.status(HttpStatus.BAD_REQUEST)
            .body(Result.error(400, "缺少必填参数: " + e.getParameterName()));
}
```

**与已有 handler 的分工**（三者都是 400，但成因不同，提示语要能让人一眼看出改哪儿）：

| 异常 | 场景 | 提示 |
| --- | --- | --- |
| `MissingServletRequestParameterException` | 根本没传参数 | 缺少必填参数: courseId |
| `MethodArgumentTypeMismatchException` | 传了但类型不对（`page=abc`） | 参数类型不正确: page |
| `MethodArgumentNotValidException` | 传了但校验不过（`status=9`） | 逐字段的中文提示 |

**这条缺陷的价值**：它证明了 Controller 切片测试这一层的必要性。纯 Service 单测测不到（异常发生在参数绑定阶段，还没进 Service）；端到端测试也测不到（那些用例都传了参数）。**"故意传错"的测试才能覆盖参数绑定这一层**。

### 5.6 请假审批后补建考勤的已知偏差（严重度：低，设计权衡非缺陷）

**现象**：请假审批通过时，区间内每一天都会被写成「请假」考勤——包括**本来没有排课的日子**（周末、寒暑假、该课程当天没课）。

**为什么这么设计**：学生通常是**提前**请假（今天提交下周的假），那时未来那些天还没有考勤记录。如果只改已有记录，等老师那天打开点名名单时，这个学生显示"未点名"，老师并不知道他请假了，很可能随手点成旷课——请假审批就白批了。所以必须补建，让老师一点开名单就看到「请假」。

**代价**：出勤统计的分母（总考勤次数）会因为这些补建记录而变大，出勤率**略微偏低**。

**为什么接受这个代价**：
1. 本项目没有"课表"实体，无法判断哪天真的有课——要做对必须先建 `course_schedule` 表，这是二期工作；
2. 出勤率偏低比"请假批了却记成旷课"要轻得多（前者是可解释的统计偏差，后者是实打实的数据错误）；
3. 补建只在审批那一刻发生一次，不会持续污染后续数据。

**真要修的正确做法**：引入 `course_schedule(course_id, weekday, session_no)` 课表，审批通过时按课表展开实际有课的日期再写考勤。在那之前，宁可有这个可解释的偏差，也不要为了数字好看而漏写。

**这也解释了为什么第 93 条测试是逐天断言**：如果将来改成按课表展开，那条测试会立刻红——它锁住的正是"区间内每一天"这个当前行为，改行为时必须有意识地改测试，而不是悄悄变了没人知道。

### 5.7 用户审核列表缺省分页参数导致 500（严重度：中，实测演示账号时发现）

**现象**：`GET /admin/user` 不带任何参数 → **500**；只带 `page` → 500；只带 `pageSize` → 500；**两个都带 → 200**。

**定位**：`UserReviewQueryDTO` 的 `page`/`pageSize` 两个字段**没有默认值**：

```java
@Min(value = 1, message = "页码最小数为 1")
private Integer page;              // ← 没有 = 1

@Min(value = 1, message = "每页条数最小为 1")
@Max(value = 100, message = "每页条数最大数为100")
private Integer pageSize;          // ← 没有 = 10
```

`@ModelAttribute` 绑定时空缺的字段保持 `null`，一路传到 `UserServiceImpl.page`：

```java
Page<User> page = userMapper.selectPage(new Page<User>(
        userReviewQueryDTO.getPage(),        // null
        userReviewQueryDTO.getPageSize()),   // null
        ...);
```

`new Page<>(null, null)` 内部对 `long` 拆箱 → `NullPointerException` → 落 `Exception` 兜底 → 500。

**为什么是"一个 DTO 漏了"这种低级错误**：项目里 7 个 QueryDTO，其余 6 个（`StudentQueryDTO`、`ClazzQueryDTO`、`CourseQueryDTO`、`ScoreQueryDTO`、`EnrollmentQueryDTO`、`LeaveQueryDTO`）**全部有默认值**，唯独这个漏了。典型的"照抄旧 DTO 时漏掉一行"。

**为什么之前 309 条测试都没发现**：

| 测试层级 | 为什么测不到 |
| --- | --- |
| Service 单测 | `page()` 用 `when(mapper.selectPage(any(), any()))` 打桩，DTO 是测试自己 `new` 出来并 `setPage(1)` 的，永远不是 null |
| Controller 切片 | 现有用例都写了 `?pageSize=500`、`?status=0` 这类**带参数**的 URL，`page`/`pageSize` 恰好都没传——但也没断言它们的值 |
| 端到端 | 同上，前端页面永远传 `page=1&pageSize=10` |

**只有"完全不带参数"或"只带一个参数"的请求才会撞上**。这和 5.5 的缺参数 500 是同一族问题：**参数绑定这一层，只有故意少传才能测出来**。

**修复**（2 行）：`page` 默认 `1`、`pageSize` 默认 `10`，与其余 6 个 DTO 对齐。

**回归测试（3 条，`AdminUserControllerTest`）**：

| 用例 | 断言 |
| --- | --- |
| `page_noParams_usesDefaults` | 不带参数 → 绑定后 `page=1, pageSize=10` |
| `page_onlyPage_defaultsPageSize` | 只传 `page=2` → `pageSize` 回落 `10` |
| `page_onlyPageSize_defaultsPage` | 只传 `pageSize=5` → `page` 回落 `1` |

**断言的是"绑定后的 DTO 已带默认值"，不是只断言 200**——因为返回 200 也可能是别的原因，而字段是 null 才是根因。

**验证这 3 条测试真的有效**：临时把默认值删掉重跑 → **3 条全红**；恢复 → 全绿。这一步不能省，否则无法区分"测试在守护"和"测试在空转"。

**顺带做的全量审计**：`grep "new Page<"` 检查全部 6 处 `selectPage` 调用，确认其余 5 处的 DTO 都有默认值，只有这一处有风险。

### 5.8 数据库 schema 落后 5 个迁移脚本，导致三个功能页全部 500（严重度：高，用户实测发现）

**现象**：用户点「成绩分析」→「服务器内部错误」。实测 6 个 `/stats/*` 接口**全部 500**；继续排查发现考勤列表、考勤统计、请假列表也是 500。

**直接原因**：

```
ERROR 1054 (42S22): Unknown column 's.deleted' in 'where clause'
```

`score` 表没有 `deleted` 列，而 `StatsMapper` / `ScoreMapper` 的手写 SQL 里写着 `s.deleted = 0`。

**真实原因（比一个列缺失严重得多）**：当前 3306 库**落后 5 个迁移脚本**。

| 脚本 | 作用 | 缺失后果 |
| --- | --- | --- |
| V6 | 删 enrollment 多余的 `deleted` 列 | 残留死列（无害） |
| V7 | 成绩唯一键改「一人一考试类型」 | **一人一课只能录一条成绩**，录期中后再录期末 409 |
| V8 | 改密时间提到毫秒 | **改密后旧 token 不失效的安全漏洞重现** |
| V9 | 建 `attendance` 表 | 考勤功能全部 500 |
| V12 | 建 `leave_request` 表 | 请假功能全部 500 |
| V10 | 演示种子数据 | 图表无数据 |

**`score.deleted` 为什么任何脚本都补不上**——这是本次最有价值的发现：

`V2__schema_refactor.sql` 里 score 的建表语句**确实写了** `deleted` 列，但用的是 `CREATE TABLE IF NOT EXISTS`：

- 表不存在 → 按语句建表，列会建出来
- **表已存在 → 整条语句被跳过，什么都不做**

也就是说，凡是在 V2 之前手动建过 `score` 表的环境，这一列**永远是缺的**，而且后续无论重跑多少次 V2 都补不上。**「建表语句里的字段后来改过」对已存在的表完全无效**——这是数据库迁移里最容易被忽略的漂移来源。

**为什么之前的 312 条测试全绿也没发现**：

| 测试层级 | 为什么测不到 |
| --- | --- |
| Service 单测 | Mapper 全是 Mockito 打桩，SQL 根本没执行 |
| Controller 切片 | 同上，`@MockitoBean` 掉 Service，不碰数据库 |
| 端到端 | 跑在**临时库 3307**（V1~V12 全新建库），schema 是完整的；而用户的 3306 库是历史遗留、缺迁移 |

**这是"测试全绿但线上炸"的典型**：测试环境和真实环境的 schema 来源不同（一个从零建库、一个是增量升级），后者才是真实用户的处境。

**修复**（分三部分）：

1. **`sql/V13__score_deleted_restore.sql`（新增）**——用 `information_schema` 判断列是否存在，不存在才 `ALTER TABLE ADD COLUMN`，可重复执行。列设为 `NOT NULL DEFAULT 0`（与其余 4 张表一致）：若允许 NULL，`WHERE s.deleted = 0` 对 NULL 判定为 UNKNOWN，那些行会被统计**静默漏掉**——这种"数字悄悄变小"比报错更难发现。
2. **`sql/verify_schema.sql`（新增，只读）**——把「代码期望的 schema」写成 SQL 断言，一条命令输出 `total_mismatches`。检查 4 类：缺表 / 缺列 / 缺索引 / 类型精度不符，每个不符项都带 `fix_hint` 指明该跑哪个脚本。修复前 `total_mismatches = 9`，修复后 `= 0`。
3. **`Score` 实体补 `@TableLogic`**——补了列还不够，MP 自动生成的 SQL 需要注解才会注入 `deleted = 0` 条件。

**`@TableLogic` 的作用范围必须说清**（这是本项目第二次踩这个点）：

- **只影响** MyBatis-Plus 自动生成的 SQL：`selectById` / `selectList` / `selectPage` / `deleteById`
- **完全绕过** 手写的 `@Select`——所以 `StatsMapper` 里的 `s.deleted = 0` 必须手写

两条路各自负责，缺一不可。只加注解不写 SQL → 统计把已删成绩算进去；只写 SQL 不加注解 → `selectById` 能查到已删记录。

**验证**：迁移后 `total_mismatches = 0`；312 条测试全绿；端到端复测 **12 个受影响接口全部 200**（6 个 stats + 考勤 2 个 + 请假 1 个 + 学生端 3 个），修复前这些全是 500。

**空数据边界同时验证**：空课程 3 的分数段返回 `[{0-59:0},{60-69:0},...]` 五个段全 0（不是空数组、不是 null）——这是 ECharts 能正常画图的前提。

**顺带确认的取舍**：**跳过 V6**。它会 `DROP COLUMN enrollment.deleted`，而该列当前无任何代码引用（`Enrollment` 实体没有该字段，手写 SQL 也只引用 `student`/`course`/`s` 的 deleted）。删掉它没有功能收益，`DROP COLUMN` 又不可逆——保留一个无害的残留列比执行破坏性变更稳妥。已写进部署说明。

### 6.1 阶段11：ECharts 按需引入的实测结果

图表是这个项目里最容易把包体积搞崩的依赖。**全量引入 `import * as echarts from 'echarts'` 约 1MB**，会把之前按需引入 Element Plus 省下的 47% 全吃回去。所以 `BaseChart.vue` 用的是精确按需：

```js
import * as echarts from 'echarts/core'          // 只引入内核
import { BarChart, LineChart, PieChart } from 'echarts/charts'
import { GridComponent, TooltipComponent, TitleComponent, LegendComponent } from 'echarts/components'
import { CanvasRenderer } from 'echarts/renderers'
echarts.use([...])
```

实测体积（`npm run build`）：

| 产物 | 体积 | gzip | 说明 |
| --- | --- | --- | --- |
| `index-*.js`（主包） | **458.66 kB** | 162.12 kB | 引入 ECharts 前是 453.49 kB，**只增加 5.17 kB** |
| `StatsView-*.js` | 560.62 kB | 190.08 kB | ECharts 全部在这里，**路由懒加载，不进首屏** |
| `AttendanceView-*.js` | 126.04 kB | 35.96 kB | 同上，按需加载 |

**关键结论**：主包只增加了 5KB，ECharts 的 560KB 被路由懒加载隔离在 `StatsView` 这个独立 chunk 里——用户不打开成绩分析页就永远不会下载它。这是"按需引入 + 路由懒加载"两层防护叠加的效果。

**BaseChart.vue 里三件必须做对的事**（每件做错都是隐性 bug）：

1. **`dispose()`**：不释放就是内存泄漏，切十次页面就有十个 ECharts 实例挂在 DOM 上。
2. **`ResizeObserver` 而不是 `window.resize`**：侧边栏折叠不触发 window resize，但会改变容器宽度——用 window 事件图表会糊成一团。
3. **`setOption(option, true)` 第二个参数 `notMerge = true`**：默认是"合并"模式，数据变少时旧数据会残留（比如从 5 段变 3 段，图上还是 5 根柱子）。

**暗色主题适配**：ECharts 默认配色是给白底设计的，直接用在深色页面上文字会看不清（深灰字 + 深灰底）。`BaseChart.vue` 里统一注入 `textStyle: { color: '#c8c8cc' }` 和透明背景，各页面的 option 只关心数据和业务配色。

**未覆盖**：本次没有做前端 E2E（浏览器自动化点击）。前端页面的功能验证依赖你此前的手工验收（见 `docs/验收测试清单.md`）以及 `vite build` 的编译期检查。如果需要前端自动化测试，可以后续引入 Playwright，但那属于额外工程投入，不是当前阶段的必要项。
